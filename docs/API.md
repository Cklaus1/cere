# API and control protocol

M1 begins with a documented subset of OpenAI-compatible chat completions routed to a proven backend. Unsupported parameters fail explicitly. Preserve tokenizer/template/tool rendering and response finish reasons. Do not advertise all OpenAI APIs merely because one route works.

The first section below is what `cered` (`crates/cere-runtime`) serves today in front of one pinned SGLang server. Everything after it is the design contract; where the two differ, the implemented section states the shipped behavior.

## Implemented M1 subset (`cered`)

Evidence classes are in [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md) and [VALIDATION_REPORT.md](VALIDATION_REPORT.md). Config keys named here are runtime config revision 2 ([CONFIGURATION.md](CONFIGURATION.md)).

| `POST /v1/responses/{id}/cancel` | bearer | Always `404 not_found` (no response store). Only with `api_compat_responses`. |

No other route exists: no legacy completions, embeddings or capabilities endpoint. The operator routes exist only when `[auth] operator_token_env` is configured.

**Auth.** `Authorization: Bearer <token>`. The token alone selects the scope (`[[auth.scopes]]`); it is compared in constant time against every configured token. A missing or unknown token gets `401 unauthorized` with `WWW-Authenticate: Bearer`; with `[auth] keyless_scope` configured a request without an `Authorization` header is that scope instead (a present but unknown token is still `401`; operator routes unchanged). A request or session of another scope answers exactly like an unknown id (`404`). The operator token (`[auth] operator_token_env`) is not a scope: it authorizes only the operator routes, and a client route answers it `401`.

**Errors.** Every error body is `{"error":{"message","type","code","param"}}`. `type` is `invalid_request_error` or `server_error`; `param` names the offending field path (`messages[2].content`, `stream_options.foo`) or is `null`. Once a request has been accepted, responses carry `X-Cere-Request-Id`, and a failure body also carries a `cere` object with `state` and `reason`.

### Readiness

Each backend worker (one per `[[deployments.replicas]]` entry of every `[[deployments]]` entry, or one on `scheduler.devices[0]` in the single form; the worker id is the device, [CONFIGURATION.md](CONFIGURATION.md)) has its own background probe, every 5 s, against its own `GET /get_server_info` and `GET /v1/models` only. `/readyz` serializes the cached results and never contacts a backend itself. A worker is ready when: both endpoints answered, every `[deployments.expect]` value of its entry except the recorded-only `image_digest` equals the server's value, its entry's served model name is listed, and a one-token greedy smoke request passed for the current backend identity. The smoke waits for an admission slot on its own worker like any request (it counts against that worker's cap and `admission.max_backend_inflight`) and never runs on another worker; a smoke call that ends without a response has its rid aborted. A probe that cannot confirm the identity forgets it, so a returning backend is smoked again. After a journal write failure (the ledger refuses every later admission until a restart) the server is not ready with the process-level problem `journal_poisoned`, whatever the probes say. The body:

```json
{"ready": true, "stopping": false, "problems": [], "tenancy": {…},
 "workers": {"gpu0": {"state": "ready", "epoch": 1, "ready": true, "instance_id": "sglang-…", "served_model_name": "…",
                      "smoke": {"state": "passed", "instance_id": "sglang-…"}, "problems": [], "probed_at_unix_ms": 1791000000000,
                      "node": "local", "model_generation": null, "lease_ms_remaining": null, "term": null,
                      "inventory": null, "inventory_sha256": null, "model": null},
             "worker-a": {"state": "joining", "epoch": null, "ready": false, "instance_id": null, "served_model_name": "…",
                          "smoke": {"state": "pending"}, "problems": [], "probed_at_unix_ms": null,
                          "node": "remote", "model_generation": null, "lease_ms_remaining": null, "term": null,
                          "inventory": null, "inventory_sha256": null,
                          "model": {"managed": null, "desired": "none", "state": null, "lock_sha256": null}}}}
```

| Field | Meaning |
|---|---|
| `ready` | at least one worker (local or remote) ready, no process-level problem, and not stopping |
| `stopping` | graceful shutdown has started |
| `problems` | process-level `[{field, detail}]` only, e.g. `journal_poisoned`; worker problems are in `workers` |
| `tenancy` | `shared_backend_tenancy`, `allow_cross_scope_prefix_cache`, `prefix_cache_isolation` (effective value: `none` or `cache_salt`), `scope_count` (Q9 posture, from config) |
| `workers` | one object per worker id (keys sorted), local workers and every `[[federation.workers]]` entry; every entry has the 15 fields below |
| `workers.<id>.state` | the worker's registry state, lowercase: `joining`, `ready`, `suspect`, `lost`, `draining`; only a `ready` worker gets new requests |
| `workers.<id>.epoch` | local: the worker epoch (≥ 1, journaled, increases on a new backend launch and on a rejoin after Lost, never reused across restarts). Remote: the epoch the agent registered in this term, `null` before an accepted Register |
| `workers.<id>.ready` | local: this worker's probe and smoke passed and its state is `ready`. Remote: its state is `ready` |
| `workers.<id>.problems` | `[{field, detail}]`. Local: empty when the worker is ready, except the advisory native `grammar` problem (below); `field` is the pinned key, `served_model_name`, `smoke`, `probe`, `grammar` or the unreachable endpoint. Remote: the failed checks of the current Joining round (below) |
| `workers.<id>.probed_at_unix_ms` | local: time of the worker's latest probe. Remote: coordinator receive time of the last accepted heartbeat of this incarnation. `null` before either |
| `workers.<id>.served_model_name` | from config (local: its `[[deployments]]` entry's `served_model_name`; remote: `[federation.workers.expect] served_model_name`) |
| `workers.<id>.instance_id` | local: `sglang-<16 hex>` derived from base URL, served name, pinned values and, when reported, the backend launch (`random_seed` and `startup_time` of `get_server_info`); `null` until every pin matched. Remote: the `instance_id` of the inventory read in this round, `null` before it |
| `workers.<id>.smoke` | `{"state":"pending"}`, `{"state":"passed","instance_id"}` or `{"state":"failed","instance_id","detail"}`; a remote worker starts every Joining round at `pending` |
| `workers.<id>.node` | `local` (served by this `cered` process) or `remote` (a `cere-worker` agent) |
| `workers.<id>.model_generation` | remote: the `model_generation` of the last accepted heartbeat; local: `null` |
| `workers.<id>.lease_ms_remaining` | remote: what is left of the coordinator-side admission lease view (`0` once expired), `null` before the first grant of this incarnation; local: `null` |
| `workers.<id>.term` | remote: the coordinator term it registered under (this process's epoch), `null` before an accepted Register in this term; local: `null` |
| `workers.<id>.inventory` | remote: the inventory document read by `DescribeResources` in this round (`schema_version`, `worker_id`, `served_model_name`, `tp_size`, `kv_cache_dtype`, `max_running_requests`, `instance_id`, `model_generation`, `admission_state`, `gpus`, `models`, `artifacts`), `null` before it; local: `null` |
| `workers.<id>.inventory_sha256` | remote: lowercase hex SHA-256 of the exact `DescribeResources` bytes, `null` before it; local: `null` |
| `workers.<id>.model` | remote (M3.6): `{managed, desired, state, lock_sha256}`: `managed` `true` (the agent owns the backend lifecycle), `false` (last described in attached mode) or `null` before the first `DescribeResources` since this start; `desired` the operator's residency intent `none`, `resident` or `unloaded` (journaled, survives restarts); `state` the last described model state (`attached`, `unloaded`, `loading`, `ready`, `draining`, `unloading`, `failed`) or `null`; `lock_sha256` the last described model's lock or `null`. All four survive a new Joining round, Lost and a re-registration. Local: `null` |

**Remote workers (M3.5, M3.6).** A configured remote worker reads `joining` with every incarnation field `null` until its agent's Register is accepted in this term; a `cered` restart is a new term, so every remote worker starts there again. After an accepted Register the coordinator drives one Joining round at a time: `DescribeResources` (the exact bytes must hash to the agent-reported `inventory_sha256`), the `[federation.workers.expect]` pins, reconciliation (every operation the agent holds that no live request of this incarnation owns is cancelled), then, once the agent reports admission state `open`, a one-token unary smoke, then `ready`. A managed worker (M3.6) whose model is not `ready` under this `cered`'s deployment lock, or whose `desired` is `unloaded`, skips the pins, reconciliation and the smoke and stays `joining`. Remote `problems` fields: `inventory` (the call failed or the document is invalid), `inventory_sha256` (hash mismatch), `served_model_name`, `tp_size` or `kv_cache_dtype` (`expected <pin>, the worker reports <value>`), `reconcile`, `smoke`, `lock_mismatch` (a managed worker's model is under another lock than the coordinator's; no lifecycle call is sent) and `residency` (a sentence naming the method and operation id of the `LoadModel`/`UnloadModel` the coordinator sent for the operator's intent, then either `ended <reason code>` at its terminal or `refused: <status>` when the agent refused the call; parse it as text, not as a bare reason code). A remote worker returns from `ready` to `joining` (a new round, `smoke` `pending` again) on a new model generation or inventory hash, a non-`open` admission state, an expired lease view, and, for a managed worker only, `desired` becoming `unloaded` or a described model state other than `ready`. Ages use coordinator receive time of the last accepted Register or heartbeat: a `ready` worker reads `suspect` once its lease view expired or after `suspect_after_ms`, and `lost` after `lost_after_ms`; a `joining` worker reads `lost` after `lost_after_ms`. A Lost epoch never rejoins; the agent registers a higher one. Drain of a remote worker: [operator routes](#operator-routes-drain-and-undrain); load and unload: [below](#operator-routes-load-and-unload). Protocol details: [WORKER_PROTOCOL.md](WORKER_PROTOCOL.md).

A worker whose probe fails or whose pins drift turns Suspect and gets no new requests; after `scheduler.worker_lost_after_ms` (default 60 s) it is Lost. A probe that matches every pin under the worker's own `instance_id` counts as seen, so a worker whose re-smoke waits for one of its own slots stays Suspect at its epoch (never Lost) and turns Ready once the smoke passes. Other workers keep serving. Builds before M3 served the single backend's fields at the top level; clients must read them under `workers`.

When `get_server_info` reports `random_seed` and `startup_time`, they identify the backend launch: they enter `instance_id` but never `problems` (they are observations, not pins). When the pins match under an `instance_id` different from the one last smoked (a relaunch, also one seen only after an outage), `cered` publishes not-ready with `smoke` `pending` and one problem `{"field":"smoke","detail":"pending: backend launch changed"}` before the new launch is smoked, then ready with the new `instance_id`, and logs `cered readiness: backend launch changed instance_id=<old> -> <new>; smoking again` on stderr. Without those fields (or with either `null`) `instance_id` is the pins-only value.

### `GET /v1/models`

One card per `[[deployments]]` entry, in config order (M5 D10, `crates/cere-runtime/src/server.rs:381-388`); a
single-entry config lists one:

```json
{"object": "list", "data": [{"id": "gemma-4-e4b-it", "object": "model", "created": 0, "owned_by": "cere",
                             "max_model_len": 32768}]}
```

`max_model_len` is that entry's deployment profile `max_context_tokens` (the field SGLang and vLLM report);
`created` is always `0`. `GET /v1/models/{id}` answers the card of the entry serving `id` (the rest of the path, so an
`org/model` name is sent unencoded as OpenAI clients do) and `404 model_not_found` (`param` `model`, the same error a
chat request naming that model gets) for any other. Both need a client bearer token and answer from config,
regardless of readiness: whether a model can take work right now is `/readyz`.

On the native profiles the card's `max_model_len` is 200,000 on `-v29` (`native-g0-spec.toml`) and 262,144 (the
model's `max_position_embeddings`) on `-v44` (the opt-in `configs/runtime/native-g0-spec-262k.toml`) and `-v52`
(`-v44` with PrefixHit's alternative prefix-cache edges, `native-g0-spec-v52.toml`, and production `prod-t4.toml` from
the production window that installs it; ctx262 design note). There prompt tokens +
`max_tokens` up to 262,144 are admitted, and above it the request is `400 context_length_exceeded` as before. Each
admitted request reserves min(context, prompt + `max_tokens` rounded up to 64) tokens of the `kv_pool_tokens` pool
(524,288 on `-v44` and `-v52`) at create (`native/serve.rs` `generate`). A request whose reservation doesn't fit beside the open
sessions waits in the card's FIFO until pages are released (`SessionQueue::create`); its deadline still applies.
Up to 200,000 tokens the 262,144 context changes no output (ctx262 design note CX-R4, CX-R7). No profile
goes past 262,144 (that needs rope scaling, ctx262 design note F10).

### `GET /get_server_info`

server-info design note. SGLang's server-info route, so a client that vets an SGLang server before it sends a
prompt (Chief's `local-sglang` provider) can vet `cered`. Same auth as `GET /v1/models` (no header with
`[auth] keyless_scope`). Every value is read from the running process:

| Key | Value |
|---|---|
| `version` | `cered <crate>; package v<PACKAGE_VERSION>`, as `cered --version` |
| `served_model_name` | the served model; with several deployments (M5) the list, in config order |
| `context_length` | the served context (one deployment; `null` with several) |
| `max_running_requests` | `admission.max_backend_inflight` |
| `host`, `port` | the bound listener's address (`server.bind` is always `127.0.0.1`) |
| `log_requests` | `telemetry.raw_content` (always `false`: lines and journals are metadata only, [OBSERVABILITY.md](OBSERVABILITY.md#access-log)) |
| `log_requests_target` | `"stderr"` if content were logged, else `null` |
| `crash_dump_folder`, `kv_events`, `kv_events_config`, `spec_trace_dir`, `msprobe_dump_config` | `null` (no such feature) |
| `enable_trace` | `false` |
| `hicache_storage_backend` | `"nvme"` with `[state] nvme_spill_enabled`, else `null` (host-RAM spill is not storage) |
| `debug_tensor_dump_output_folder` | `"/v1/cere/research/captures"` with `[deployments.native.research]` (activation captures leave the process), else `null` |
| `cere` | `config_hash`, `telemetry_level`, `raw_content`, `usage_journal`, `host_spill_enabled`, `research`, `federation_listen` (worker RPC listener or `null`), `unverified_workers` |

A `sglang_http` backend or a federation worker keeps its own logging and dump settings, which `cered` cannot see.
With any such worker it is listed in `cere.unverified_workers` (`<worker_id>: sglang_http <base_url>` or
`<worker_id>: remote`), `log_requests` is `null`, and each other retention key whose `cered` value is none is left
out, so a vetting client refuses instead of trusting an unchecked backend.

### `POST /v1/chat/completions`

Checks run in this order; the first failure answers and nothing reaches the backend: auth (`401`), shutting down (`503 shutting_down`), not ready (`503 not_ready`, message names the failing readiness fields), body over `api.max_request_body_bytes` (`413 request_too_large`), JSON (`400 invalid_json`), body fields, headers.

Accepted body fields (`null` counts as absent). Any other top-level field, known to OpenAI or not, is `400 unsupported_parameter` with `param` set; `cache_salt` is rejected this way, and the sampling, M2.12 and grammar fields the profile does not declare are refused with the same code (`crates/cere-runtime/src/validate.rs` `ALLOWED_FIELDS`, 31 fields since M2.8). ApiLenient (api-lenient design note) adds the closed alias list `MAPPED_PARAMS`, the inert list `INERT_PARAMS` and a remedy message for each refused OpenAI field (table rows below). omp (`@oh-my-pi/pi-coding-agent` 18.12.6) works without a `compat` block in `models.yml`: its `enable_thinking`, `preserve_thinking` and `max_completion_tokens` 32768 are served on every native profile with a ≥ 64K context (their `api.max_output_tokens` is 32,768 since AL-5); set `contextWindow` to the profile's `max_context_tokens`.

| Field | Rule |
|---|---|
| `model` | required string; selects the `[[deployments]]` entry whose `served_model_name` equals it (M5 D5); any other is `404 model_not_found`, message `model '<model>' is not served here; served models: <a>, <b>` (every served model, config order; `crates/cere-runtime/src/validate.rs:320-333`). The other field rules are that entry's. After validation, a model none of whose workers is ready is `503 not_ready` (`backend not ready: no worker of <model> is ready`), also while another model's workers are ready |
| `messages` | required non-empty array of at most `api.max_messages` objects. system: `role`, string `content`, optional `name` (below). user: `role`, optional `name`, `content`, a string or an array of 1 to 64 parts (below). assistant: `role`, `content` (string, or `null` with non-empty `tool_calls`), optional `tool_calls` = `[{id, index?, type?: "function", function: {name, arguments}}]` (`index` an integer ≥ 0, accepted and dropped; `arguments` a string that parses to a JSON object, kept byte-exact), optional `reasoning_content` (a string, passed to the chat template, which renders it inside the turn's `<think>` block on both backends; `null` or `""` = absent; it is part of the request digest but not of session prefix digests, so an echoed reply continues its session with or without its reasoning; another type is `400 invalid_value`; owner 2026-10-17, O113); `tool_calls: null` counts as absent. Every message (system, user, assistant, tool) may carry a string `name` (OpenAI's participant name; tool-eval-bench sets it on every tool result; accepted and dropped: the pinned chat template never reads it, so it is neither forwarded nor digested; another type is `400 invalid_value`; tool messages: Main 2026-10-17, O113). tool: `role`, `content` (a string, or an array of 1 to 64 parts, below: `text` and `file` parts (DocInput) render as their joined string; with an `image_url` part (VisionLong C7) the parts are kept), string `tool_call_id`, optional `name`. So a response's `choices[0].message` echoed as is is accepted. A missing `role`, `content`, `tool_call_id` or `tool_calls[j]` `id`/`function`/`name`/`arguments` is `400 missing_required_parameter`; another key or role, a non-null `reasoning_content`, non-string `content` outside a user or tool message and `content: null` without `tool_calls` are `400 unsupported_parameter`; any other wrong value is `400 invalid_value`; each names its path (`validate.rs:662-823`) |
| `messages[i].content` parts (M2.13) | user and tool messages only (VisionLong C7: a tool result may carry screenshots; the pinned template renders a tool message's parts inside its `<tool_response>` as it renders a user message's, and a text-only tool array renders like its joined string, so text requests encode unchanged; DocInput: a tool message's `text`/`file` parts without an image render as their joined string). Each part is exactly `{type: "text", text}`, `{type: "image_url", image_url: {url, detail?}}` or `{type: "file", file: {file_data, filename?}}` (below); another `type` (`video_url`, `input_image`, `image`, ...) or key (`max_dynamic_patch`, `cache_control`, ...) is `400 unsupported_parameter` naming it, and `detail` may only be `"auto"`. A text-only array renders like its joined string. `url` must be `data:image/png;base64,` or `data:image/jpeg;base64,` followed by strict RFC 4648 base64 (no whitespace); http(s), `file://`, paths and other media types are `400 invalid_value` before any backend call, and the message never quotes the URL. The PNG IHDR or JPEG SOFn header is read without decoding: each side at most 8,192 px, aspect ratio at most 200, and the image costs (H/32)·(W/32) tokens after the processor's resize to multiples of 32 within 65,536..16,777,216 px. At most 32 images per request (history included) and 4,096 tokens per image (16,384 patches; `image.rs` `MAX_IMAGES`, `MAX_TOKENS_PER_IMAGE`); the request's image tokens together must fit the profile's image context (the smallest `max_context_tokens` of its image decode combinations, capped by the deployment's context: 2,048 on `-v6`, 200,000 on `-v43`); each violation is `400 invalid_value` naming the URL. Images need the profile's image decode combination for the request's sampler mode (the SGLang Qwen profile declares greedy and sampled, unmeasured; the native vision profiles `-v6` and `-v43` declare theirs; other native and gemma profiles have none) and a deployment without federation workers, else `400 unsupported_parameter` naming the part. On native an image request speculates only when the profile has a `verify`/`image`/`text` combination for its sampler mode and enters the prefix cache only with a `prefill`/`image` combination (`-v43` has both; `-v6` neither, so it keeps `CERE_WORK_NO_SPECULATION` and no capture). `-v43` runs the image processor on the CPU (sidecar `--image-device cpu`, m213l design note D-L8): a PNG gives `pixel_values` bit-identical to the `cuda:0` processor at every size, and a repeated image is served from the sidecar's memo cache. A JPEG is decoded there by PIL, not nvJPEG (decoder exception D-L9: `pixel_values` differ by at most 0.36 at identity size; VL-16 measures the effect on answers). Parts forward to SGLang value-exact (data URL byte-equal, `detail` only when sent) and digest as sent, so a one-byte image change is a different session history (`validate.rs`, `image.rs`) |

**Mid-conversation system messages (ApiFit, api-fit design note AF-L1; a CERE extension).** The pinned chat template accepts a system message only as `messages[0]` and raises on any later one, and SGLang and vLLM answer such a request `400`. CERE accepts a `system` message at any position: `messages[0]` is the system block as before, and a system message at index ≥ 1 is validated as one and then renders in place as a user message whose content is `<system-message>\n` + its content + `\n</system-message>`. Everything before it stays a valid cached prefix (the fold only inserts that turn). The folded form is what reaches the backend (both kinds), the request digest and the journal; a request whose only system message is first, or that has none, is byte-identical to before. The marks carry the message's system authority to the model; they are plain text, not a trust boundary (the caller owns both roles). Anthropic Messages and Responses requests converge on the same rule (below).

**Native backend (`deployments.kind = "native_cuda"`, M2.2b; one entry only).** Since M2.7 (profile `native-g0-qwen38-flash-next-v7`) the executor samples on the device: `temperature`, `top_p`, `top_k` (each absent: the model's `generation_config.json` value read at upload, 1.0 / 0.95 / 20 for Qwen3.8-Flash-Next, as SGLang's `sampling_defaults="model"`; m27 design note D10, Q4 (a)), `min_p`, `seed`, the three penalties and `logit_bias`, and returns per-token `logprobs` with up to 20 `top_logprobs`. T < 1e-6 (or `top_k` 1) is greedy and takes the unchanged greedy path. A sampled request needs a library that reports `native_sampler` = 1; the start check refuses a profile with sampled rows otherwise. Each row of a batched decode step samples with its own sampling, output counts and counter key (sampled `row_counts` `[1, 2, 3, 4]`; ledger CR4), so a sampled session commits the same tokens whatever else shares the round. Native sampled output and logprobs are native's own: they are not SGLang's tokens or values (the logits differ; G1 has not passed), and a `seed` reproduces native's draws, not SGLang's. CERE renders `choices[].logprobs` in SGLang's shape; a `-inf` alternative is `null` in a stream and omitted from a unary body (m27 design note D7, Q7). The tokenizer sidecar encodes the chat (with tools, rendered by the model's template unless `tool_choice` is `none`) once and validates tool schemas as SGLang does (refusal: `400 invalid_value` at `tools[i].function.parameters`, `native/serve.rs:90-99`); prompt tokens + `max_tokens` above `deployments.native.max_context_tokens` is `400 context_length_exceeded`. One executor session runs the request; the body and SSE chunks have the SGLang shape (reasoning split by the Qwen3 parser, tool calls by CERE's port of SGLang's qwen3_coder detector, `native/tool_parser.rs`), `cached_tokens` is the prompt tokens the PREFILL took from the native prefix cache (M2.10, m210 design note D10; with `n` > 1 choice 0's): always `0` on the shipped cache-off `native-g0.toml` (`-v8`, `prefix_state_slots` absent), a multiple of 64 up to floor64(`prompt_tokens` − 1) on the opt-in `-v11` profiles `native-g0-prefix.toml` / `native-g1-prefix.toml`, whose scopes never share entries (`prefix_cache_isolation = "cache_salt"`). A hit's output equals a cold run whose prefill was split at the same point, not always an unsplit cold run (D8), so the cache stays opt-in, `finish_reason` is `stop`, `tool_calls` or `length`. Stop strings are matched by `cered` per committed token (`native/stop.rs`): the text is trimmed at the match and `completion_tokens` counts through it. Cancel, deadline and disconnect cancel the executor work at the next token boundary; a cancel during prefill lands only after the whole prompt prefill, which runs as one step (up to ~15.6 s at 73,727 tokens; [EXECUTION_PLUGIN.md](EXECUTION_PLUGIN.md)).

**Thinking and token controls on native (M2.12).** The native profile `native-g0-qwen38-flash-next-v8` declares `thinking_toggle: true` (its context is 200,000, Q6), `token_controls: ["stop_token_ids", "ignore_eos"]` and `vocab_size: 248320`. Every executor ticket of a request carries `CERE_WORK_IGNORE_STOP_TOKENS` under `ignore_eos` (`cere_work.flags` bit 0) and `CERE_WORK_NO_SPECULATION` under `ignore_eos` or `min_tokens > 0`; the request's `stop_token_ids` join the model's stop tokens on every ticket.

**Added-token text on native (m214 design note N5 = b) escape, owner decision 2026-10-15).** On a `native_cuda` deployment client text never becomes a control token: any substring of system, user or tool message content (a string or each text part; on `/v1/messages` and `/v1/responses` the `tool_result` blocks and `function_call_output` items, which the adapters turn into tool messages) or of a rendered tool definition (name, description, parameters) that equals an added token of the pinned tokenizer (`added_tokens_decoder`, special or not: `<|im_start|>`, `<|im_end|>`, `<think>`, `<tool_call>`, the vision markers, …) is encoded as ordinary text. Assistant content and tool calls are not escaped: they reproduce model output, so a history re-encodes to the generated ids. Template structure and real image parts are unchanged, and literal vision-marker text never creates an image span. A request without such text encodes exactly as before. `usage.prompt_tokens`, Anthropic `count_tokens` and the session prefix hint all count these ids. The mechanism and its boundary rule are in the sidecar's module docstring ([`tokenizer_sidecar.py`](../scripts/native/tokenizer_sidecar.py)). An `sglang_http` deployment (`bench-g0`) tokenizes on SGLang's side and still maps such text to the added ids, so the two backends give different prompt ids and counts for these requests only.

**Native constrained decoding (M2.8).** The native profile `native-g0-qwen38-flash-next-v8` (D10) advertises `json_schema` (the SGLang profile's dialect and keywords), `regex`, `ebnf` and `tool_calls_constrained` for greedy and sampled `decode` at rows 1-4, never with `verify`; the grammar process supplies a per-position vocab mask that the executor applies after the penalties and before `logit_bias` (K12, SGLang's order). A native profile that advertises a grammar output is refused at readiness unless the executor reports `capabilities.native_token_mask = 1` and a second sidecar process (`--role grammar`, xgrammar from the pinned image) reports feature `grammar` and the xgrammar version of the profile's dialect within 50 s. Once ready, a grammar process that missed the 50 s compile deadline or died is killed and respawned: while it respawns, and for good if the respawned process fails its `info`, the worker's `problems` carry an advisory `{"field":"grammar"}` entry and constrained requests are refused, while the worker stays ready for unconstrained requests. The readiness probe also refuses (not ready) a grammar process whose `stop_token_ids` differ from the model's stop tokens or whose `vocab_size` differs from the model's. A constrained request runs as PREFILL(prompt, 1) with the initial mask, then one DECODE ticket whose position-0 mask follows the PREFILL token; each later committed token is stepped through the grammar and its next mask sent with `Constrain`; every constrained submit sets `NO_SPECULATION`. A grammar that terminates on a token the executor did not stop on (with `ignore_eos`, an EOS) cancels the ticket and finishes `stop` with `matched_stop` = that token; `length` mid-structure stays `length`. With `enable_thinking` the mask is deferred past `</think>` (SGLang's `ReasonerGrammarBackend`): the reasoning is unconstrained. A `grammar_step` error, a token the grammar rejects, or the grammar process dying fails the request `500 internal_error` (stream: an error event) and cancels the ticket. `min_tokens` is `400 unsupported_parameter` on native with or without a constraint (`param` `min_tokens`, before any grammar work), so D15's `min_tokens` case is a pinned refusal there.

**Constrained speculation (GrammarSpec, `-v49`).** A deployment whose runtime levers set `grammar_drafts = "on"` (profile `native-g0-qwen38-flash-next-v49`, `configs/runtime/native-g0-spec-grammar.toml`; every shipped profile keeps the default `off`) drops `NO_SPECULATION` from constrained submits; `ignore_eos`, penalties, `logit_bias` and images still set it, and `min_tokens` stays refused. The first DECODE round runs without drafts. Each later round, cered asks the executor for the round's frozen drafts (`cere_executor_round_drafts`, at most 3), the grammar process for the mask after each draft prefix it accepts (op `grammar_drafts`: a rejected draft ends the chain, a draft that terminates the grammar is not offered, the matcher is rolled back), and sends one mask per round row (`cere_executor_constrain_drafts`); with no drafts it sends the plain `Constrain`. The verify keeps only tokens the per-row masks allow, so every output token passes the grammar exactly as without drafts: a greedy constrained output equals the `off` output, while a sampled one is distribution-equal rather than bit-identical (its seeded draws move with the rounds). Only tokens the verify committed are stepped through the grammar. A failed `round_drafts` or `grammar_drafts` fails the request `500 internal_error` (stream: an error event), with no silent fallback. The capabilities JSON is the `-v29` one (the grammar outputs stay `decode`-only; no `verify` combination is declared). A config with `on` is refused at load (`problems` field `levers`) unless the executor library exports both functions and the grammar process reports feature `grammar_drafts`. The lever is restart class, and an A/B arm may only set `off`. [INFERENCE] The speculation counters (`GET /v1/cere/stats` `native_spec_verify_steps`, `native_spec_accepted_drafts`) count constrained rounds as well; `grammar_live.py` R6 reads them for the accept length.

**Tool calls and `matched_stop` (M2.4).** Calls are parsed and returned, never executed. A unary response carries `message.tool_calls` = `[{id, index, type: "function", function: {name, arguments}}]` (`arguments` a JSON string) with `content` `""` when only calls were produced; a stream sends `delta.tool_calls` fragments per `index` (`id` and `name` in the first, `arguments` text appended after). With at least one call a `stop` finish becomes `finish_reason` `tool_calls` (a success, like `stop`). `matched_stop` is the stop string or stop token id that ended the output, `null` on `length`; on a `tool_calls` finish it is `null` in a unary body and kept in the stream's finish chunk, as in SGLang (`native/serve.rs:686-705`). Native ids are `call_` + 24 hex. A session turn commits `{role: "assistant", content, tool_calls}` assembled per `index` from every chunk, the finish chunk included (`validate.rs:111-150`). A stream cut by `length` mid-call commits the arguments streamed so far, which are unbalanced JSON (`{"p": "v"`); echoing that message back is `400 invalid_value` at `messages[i].tool_calls[j].function.arguments`, as in SGLang (`tests/server_native.rs:1216-1264`). A unary `length` closes the call at the end.

**Prefix-cache isolation.** With `[[deployments]] prefix_cache_isolation = "cache_salt"` (equal across entries, M5 D2(g)) every backend chat call of a scope, unary and streamed, carries `"cache_salt": <salt>`, where the salt is the first 32 hex characters of HMAC-SHA256(`server_secret`, `"cere-cache-salt\0"` ‖ `scope_id`). SGLang namespaces its radix cache by the salt, so one scope cannot hit another scope's cached prefix. The salt is stable across restarts (the secret is), differs per scope and cannot be derived from the scope id without the secret. The readiness smoke belongs to no scope and is sent unsalted. With `none` (or the key absent) no salt is sent. A client cannot choose a salt: a request body with `cache_salt` is `400 unsupported_parameter`.

**Unary response.** The backend's OpenAI body (content, `reasoning_content`, `finish_reason`, `usage`) plus a `cere` object: `request_id`, `attempt` (always 1), `worker_id` (the device id of the worker the request was dispatched to, e.g. `gpu0`; builds before M3 sent `local`), `worker_epoch` (that worker's epoch at dispatch), `epoch`, `recipe_id`, `lock_sha256`, `instance_id`, `profile_id`, `config_hash`, `execution_mode` (the profile's: `backend_managed` on `sglang_http`, `native` on `native_cuda`), `cached_tokens`, `cache_report`, `state` (`completed`), and `session_id` + `revision` on a session turn. `worker_id` and `worker_epoch` are `null` for a request that never reached a worker (`queue_full`, deadline, `worker_not_ready`) and for requests journaled before M3. `cached_tokens`/`cache_report` follow the cached-count rule below.

**Per-deployment `cere` fields (M5 D5).** `recipe_id`, `lock_sha256`, `profile_id`, `execution_mode` and the cached-count pin (`enable_cache_report`, below) are those of the request's `[[deployments]]` entry (`DeploymentIdentity`, `crates/cere-runtime/src/api_types.rs:221-249`); `config_hash` is the one global hash. The request digest (idempotency) binds the request's `model` and the global `config_hash`.

**Cached-count rule (Q1).** `cached_tokens` is never estimated by CERE; `cache_report` is `reported` when `cached_tokens` is a number and `unavailable` when it is `null`.

| Case | `cached_tokens` / `cache_report` |
|---|---|
| the backend's `usage` has `prompt_tokens_details.cached_tokens` | that count / `reported` |
| pin `[deployments.expect] enable_cache_report = true` of the request's entry (readiness keeps the backend equal to it), the request did not end `cancelled`, and its `usage` has no `prompt_tokens_details` (SGLang omits them on a miss) | `0` / `reported` |
| no backend `usage` object (failures without usage, cut streams, the `accepted` event) | `null` / `unavailable`, whatever the pin |
| the request ended `cancelled` and its `usage` reports no count (an abort can still produce a usage chunk without details) | `null` / `unavailable`, whatever the pin |
| pin `enable_cache_report = false` and no count reported | `null` / `unavailable` |

**Finish handling.** `finish_reason` `stop`, `tool_calls` or `repetition` (native only, with `[deployments.native.loop_guard]`), or `length` with `completion_tokens` equal to the forwarded budget, completes. `length` below the budget fails `502 backend_clamped_output`. `abort` without a CERE cancel fails `502 backend_abort`. A `length` finish without `completion_tokens`, or any other finish value, fails `502 backend_protocol_error`.

**Loop guard (native, opt-in; loop-guard design note).** With `[deployments.native.loop_guard]` ([CONFIGURATION.md](CONFIGURATION.md)) a native output whose text ends repeating one block (at least `min_repeats` exact copies of a `min_period_bytes..max_period_bytes` unit covering `min_span_bytes`) finishes on that token with `finish_reason` `repetition` and `matched_stop` `null`: the text and tokens through it are kept, `state` is `completed`, and Anthropic reports `stop_reason` `end_turn`, Responses `completed`. A request whose messages end in `tool_repeat_run` identical assistant tool call -> `tool` result pairs (arguments compared without `ignore_arg_keys`) is refused `400` `{"type": "invalid_request_error", "code": "loop_detected", "param": "messages"}` before any tokenizer or executor work; the client should change course instead of repeating the call. Without the table neither happens.

**Streaming.** `200 text/event-stream`, every event a `data:` line:

1. `accepted`: a chunk with `choices: []` and the full `cere` object plus `seq: 0`, `event: "accepted"`.
2. Passthrough chunks, each with `cere: {"seq": n, "committed_tokens": null}`. `seq` increases by one per event. `committed_tokens` is always `null`: the backend does not report continuous usage. `: keepalive` comments are sent after 15 s without an event; they are not tokens and get no `seq`.
3. Success: the finish chunk (the only chunk with a `finish_reason`, and the terminal) carrying the full `cere` object with `state: "completed"` (plus session fields), then the usage chunk if `include_usage`, then `data: [DONE]`. The terminal is journaled before the finish chunk is sent.
4. Failure or cancel after the stream opened: exactly one `{"error":{…},"cere":{"seq","state","reason","usage","worker_id","worker_epoch"}}` event, then `data: [DONE]`. `worker_id`/`worker_epoch` are the dispatched worker (`null` before dispatch). `cere.usage` is the status API's `usage` object (same values and null rules) and is sent whether or not `include_usage` was requested.

Every event with a `seq` is preceded by an `id: <seq>` line (the same value as `cere.seq`); `[DONE]` and comments have none.

A failure before the stream opens is an ordinary HTTP error response. The client channel holds `api.stream_buffer_events` events; a client that leaves no room for `api.stall_timeout_ms` is cancelled `client_backpressure`, and the blocked time is recorded. If the backend finishes but the client did not receive the whole output during a cancel, the request ends `cancelled`, not `completed`.

**Context overflow.** SGLang reports an over-long prompt in two forms, both mapped to `context_overflow` (HTTP status 400 in the error object, `param` `messages`): a plain HTTP 400 whose text contains "context length" (the tokenizer's check, before any stream opens), and an error whose code is 400 and whose text contains "exceeds the maximum allowed length" (the scheduler's check). For a stream the scheduler form arrives after the backend's HTTP 200, so the client sees the opened stream end with the SSE error event (`state` `failed`, `reason` `context_overflow`); for a unary request it is an HTTP 400. Any other status, including a 500 mentioning the context length, stays `backend_error`. CERE does no length check of its own before dispatch to SGLang. On a `native_cuda` deployment cered checks prompt + `max_tokens` against the context itself: `400 context_length_exceeded`, `param` `messages`, "the prompt (N tokens) plus max_tokens (K) exceeds the context limit of C tokens". `/v1/messages` words both refusals as Anthropic does (below).

**Tool refusals on a remote worker.** On a request with `tools`, SGLang's refusal of a tool's `parameters` schema (a 400 whose message starts `Tool {i} function`) is `400 invalid_value` (`param` `tools[i].function.parameters` locally, `tools` on a remote worker, whose reason code carries no index), and a remote worker whose backend does not run the `qwen3_coder` tool parser refuses the request as `400 unsupported_parameter` (`param` `tools`) before any backend call. Locally both are plain HTTP 400s. On a remote worker a stream's SSE response opens before the worker's first event, so the client sees the opened stream end with the SSE error event (`state` `failed`, code `invalid_value` or `unsupported_parameter`), as for the scheduler's context overflow; a unary request gets the HTTP 400. Without `tools` the same backend 400 is an ordinary `502 backend_error`.

**Priority.** `X-Cere-Priority: high | normal | low` (case-insensitive, default `normal`; another value is `400 invalid_value`) orders a request among the queued requests of its own scope; see admission below. It is not part of the idempotency digest.

**Class.** `X-Cere-Class: interactive | batch` (case-insensitive; another value is `400 invalid_value`) sets the request's team-pool scheduling class (net-teleport design note 4.4, C17); absent, the scope's `[[auth.scopes]] class` (default `interactive`). See admission below. It is not part of the idempotency digest.

### Stream resume

A stream sent with `X-Cere-On-Disconnect: continue` (the only accepted value, case-insensitive; another value is `400 invalid_value`) can be resumed. Without the header a disconnect cancels as before.

- From the `accepted` event on, every event is stored in the request's resume buffer as it is created and the response reads from that buffer. A client that stalls or disconnects is detached, not cancelled: `client_backpressure` does not apply, and the request runs on under its own deadline and output budget. Its terminal state is the backend outcome. A disconnect while the request is still queued (before `accepted`) cancels in both modes.
- `GET /v1/cere/requests/{id}/events?after=<seq>` (same bearer scope) returns `200 text/event-stream` with the retained events whose seq is greater than the cursor, then follows the live stream to its terminal and `data: [DONE]`. `after` wins over a `Last-Event-ID` header; with neither, replay starts at seq 0. A non-integer `after` is `400 invalid_value`.
- One reader at a time: a new reader supersedes the current one, which receives the comment `: superseded` and is closed, never with `[DONE]` or an error event.
- A reader whose next event was evicted ends without `[DONE]`; reconnecting with its cursor then gets `410`.
- A keyed retry of a continue-mode stream gets `409 stream_not_replayable` with `error.events_url` (`/v1/cere/requests/<id>/events`) beside `error.status_url`.

| Case | Answer |
|---|---|
| unknown id, other scope, or the request is past `ledger.terminal_retention_ms` | `404 request_not_found` |
| not a stream, or a stream sent without `continue` | `409 not_resumable` |
| a request of a previous `cered` process (epoch) | `410 cursor_expired` |
| buffer released (retention) or evicted (byte bounds), or the events after the cursor evicted | `410 cursor_expired` |

Buffers are bounded per request by `api.resume_buffer_bytes` (the oldest events go first), in total by `api.resume_buffer_total_bytes` (the oldest terminal buffers are released first; with none left, the growing buffer drops its own oldest events) and in time by `api.resume_retention_ms` after the terminal (see [CONFIGURATION.md](CONFIGURATION.md)). They are memory only: a `cered` restart loses them.

### Idempotency

`Idempotency-Key` is optional (Q2). Without it every request is new and nothing is deduplicated. With it, `(scope, key)` maps to one request, compared by an HMAC-SHA256 digest of the normalized request (model, messages, budget, `temperature`, `top_p`, `stop`, `stream`, `include_usage`, and since M2.4 `tools` as its exact bytes, so key order and number spelling count, `tool_choice` when `none` with tools, `parallel_tool_calls: false`, `logprobs: true` and `top_logprobs`; since M2.7 `top_k`, `min_p`, `seed`, the three penalties and `logit_bias`; defaults are omitted (`top_k` -1, `min_p` and the additive penalties 0, `repetition_penalty` 1, an empty `logit_bias`), so an older body digests as before; `validate.rs:219-250`), the session id and expected revision, the served model, the effective deadline and the config hash. A retry must therefore repeat the same deadline header, and a config change makes an old key conflict.

| Prior request under the key | Answer |
|---|---|
| ended before it was sent to the backend (`429 queue_full`, `504` deadline while queued, `503 shutting_down`/`not_ready`/`worker_epoch_superseded` or `500 journal_error` at dispatch, cancelled before dispatch, or failed `worker_restart` after its `cered` stopped before journaling the dispatch) | none: the key was released; the retry runs as a new request |
| different digest | `409 idempotency_conflict` |
| not yet terminal | `409 request_in_progress` (a continue-mode stream past its `accepted` event: `409 stream_not_replayable` with `error.events_url`) |
| streamed | `409 stream_not_replayable` (never regenerated; a continue-mode stream adds `error.events_url`) |
| unary, completed, body retained | the original status and body with the same `X-Cere-Request-Id`; nothing runs |
| unary, body not retained (failed or cancelled, evicted, or lost on restart) | `409 response_not_retained` |
| record past `ledger.terminal_retention_ms` | `409 idempotency_key_expired` (never regenerated) |

The `request_in_progress`, `stream_not_replayable` and `response_not_retained` bodies add `error.status_url` (`/v1/cere/requests/<id>`) and the `X-Cere-Request-Id` header. Retained bodies are kept in memory only, bounded in total by `api.max_request_body_bytes`, oldest dropped first. Expired keys leave a tombstone; the tombstone list is bounded to `ledger.max_records` keys, oldest dropped first, after which a key counts as new again.

Inert fields (`user`, `metadata`, `store: false`, …; the chat field table, api-lenient design note D5) are dropped before normalization, so they are not part of the digest: a retry under the same key that differs only in them replays the first response (the replay carries the retry's `X-Cere-Ignored-Params`).

### Admission and deadlines

An accepted request waits for a slot under `admission.max_backend_inflight` (global) and `admission.per_scope_inflight`. Since M2.6 (m26 design note D12) the unit is one decode row: a request costs 1, a native request with `n` > 1 costs `n` against the global, per-scope and worker in-flight limits and the round-robin deficit, and once a cost-`n` waiter is at the head and not grantable no later waiter is granted until `n` rows are free (head-of-line reservation, so it cannot starve behind cost-1 requests). Waiters are granted by weighted deficit round-robin across scopes (`[[auth.scopes]] weight`) and, inside a scope, by `X-Cere-Priority` (high, normal, low; FIFO within a level); a waiter queued longer than `admission.aging_ms` is served as `high`. See [ADMISSION_CONTROL.md](ADMISSION_CONTROL.md#what-shipped-m1). The queue holds `admission.queue_depth` waiters; a full queue is `429 queue_full`. A deadline that expires while queued cancels the request with no backend call (`504 deadline_exceeded`). A deadline that expires while running sends `/abort_request` for the rid: the request ends `cancelled`/`deadline_exceeded` when the backend stream ends, or `failed`/`cancel_unacknowledged` if it does not end within 5 s. A slot stays charged until the backend response has actually ended, including after `cancel_unacknowledged`.

**Team pools** (net-teleport design note 4.4, S6). A worker is granted to a scope only when its effective tier for that scope (`own` for its `[[federation.workers]] owner`, else its `tier`; local workers are this install's `server.tier`) is in the scope's `allowed_tiers`, and, while the worker is owner-only (an `owner_only` window or its local `cere-worker owner-only on`), only to its owner. A request with no such worker queues and then fails `no_allowed_worker`; it never goes to a disallowed worker. When a slot frees on an owned worker, the owner's grantable waiter is served first, ahead of the round-robin; a non-owner's work on an owned worker is bounded by `admission.owner_wait_cap_ms`. Across scopes, `interactive` waiters are served before `batch` ones, and while both classes wait at least `admission.batch_floor` of the grants go to `batch`; the round-robin by weight orders scopes within a class, and `X-Cere-Priority` still orders a scope's own queue. `[[auth.scopes]] per_scope_inflight` and `max_sessions_per_scope` override the global caps for one scope, and `max_batch_inflight` caps a scope's `batch` rows.

### Status and cancel

`GET /v1/cere/requests/{id}` returns `request_id`, `state` (`accepted`, `queued`, `running`, `cancel_pending`, `completed`, `failed`, `cancelled`), `reason`, `attempt`, `epoch`, `worker_id`, `worker_epoch` (both set when the dispatch is journaled, restored after a restart, `null` before dispatch and for pre-M3 records), `stream`, `session_id`, `execution_mode`, `timings` (`queue_wait_ms`, `encode_ms`, `first_generated_ms`, `first_visible_ms`, `total_ms`, `client_backpressure_ms`; unmeasured values are `null`, and the first-token pair is only measured on streams; `queue_wait_ms` is the time in `queued` less `encode_ms`, the native pre-grant encode, which is absent for other requests, while every other timing counts from acceptance) and `usage`. Records stay queryable until `ledger.terminal_retention_ms` after their terminal.

`usage` is `{"prompt_tokens","completion_tokens","cached_tokens","cache_report"}` as the backend reported them: the token counts come from the backend's `usage` object (`null` when absent), and `cached_tokens`/`cache_report` follow the cached-count rule above. Until the backend has reported, and for a request that never received a backend `usage`, all three counts are `null` and `cache_report` is `unavailable`. The same object is journaled with the terminal, so it survives a restart for the retention period.

`POST /v1/cere/requests/{id}/cancel` (no body) returns `{"request_id","state"}`: `202` with `cancelled` when the request had not been dispatched (no backend call is made), `202` with `cancel_pending` when it was running (`/abort_request` is sent and the request settles when the backend stream ends), `200` with the terminal state when it had already ended. A client disconnect has the same effect as a cancel, with reason `client_disconnected`, except for a continue-mode stream that has opened (above). CERE only ever aborts one exact rid; it never sends `abort_all`.

### Stats

`GET /v1/cere/stats` answers for the caller's scope only; other scopes' traffic is not visible. Counters cover terminals written by this `cered` process (since `since_unix_ms`, when it opened its ledger); a restart starts from zero, and terminals replayed from the journal are not counted. Requests that a start fails `worker_restart` are counted by the new process.

On a native backend with a grammar process (a profile that advertises a grammar output, M2.8 D8) the body also carries `grammar`: `{"step_ms_p50", "step_ms_p99", "constrain_gap_ms_p50", "constrain_gap_ms_p99"}`, the nearest-rank p50/p99 in ms over the last 4,096 samples of the grammar process's `grammar_step` wall time and of the gap from a `Constrain` command (the next position's mask) to the next committed token; each is `null` before a sample. Unlike the counters it is process-wide (every scope's constrained requests) and holds timings only. Without a grammar process the key is absent.

Example for a scope with two completed requests, a miss and a hit:

```json
{"scope": "a", "requests": {"cancelled": 0, "completed": 2, "failed": 0},
 "prompt_tokens_total": 4, "cached_tokens_total": 2, "cache_reported_requests": 2,
 "cache_unavailable_requests": 0, "since_unix_ms": 1791000000000, "native_submissions": 0,
 "native_preemptions": 0, "native_grows": 0, "config_generation": 0, "effective_config_hash": "<64 hex>",
 "workers": {"gpu0": {"state": "ready", "epoch": 1, "cap": 4, "inflight": 0}}}
```

| Field | Meaning |
|---|---|
| `requests` | terminals by state; all three states are always present |
| `prompt_tokens_total` | sum of reported `prompt_tokens` |
| `cached_tokens_total` | sum of `cached_tokens` over requests with `cache_report: "reported"` only |
| `cache_reported_requests` / `cache_unavailable_requests` | terminals with `cache_report` `reported` / `unavailable` (every terminal is one of the two, including requests that never reached the backend) |
| `since_unix_ms` | when this process incarnation opened its ledger |
| `native_submissions` | process-wide (not per scope): requests the native executor accepted (`deployments.kind = "native_cuda"`; the readiness SMOKE, refusals and `context_length_exceeded` never count); always `0` on `sglang_http` |
| `native_preemptions` | process-wide: generations the native executor parked in the snapshot arena for another request (U1, `[deployments.native] preempt = true`, m211 design note D8); always `0` without `preempt` and on `sglang_http` |
| `native_grows` | process-wide: generations that used up their reserved first session and parked themselves to continue in a session of their whole budget (SE-09, `[deployments.native] reserve_output_tokens` > 0, sessions design note); the output is the same as without the grow. Always `0` without `reserve_output_tokens` and on `sglang_http`. A grow does not count in `native_preemptions` |
| `prefill_signature` | process-wide: the loaded native model's prefill selection signature, lowercase hex (`cere_model_prefill_signature`, batch-concurrency design note "Prefill selection signature"); `null` on `sglang_http`, before the native load and when the library reports none. `/readyz` shows it in the native worker's entry |
| `config_generation` | process-wide: live config reloads applied since this start (`0` as started; a no-op or refused reload does not count, [RUNBOOK.md](RUNBOOK.md#live-config-reload)) |
| `effective_config_hash` | process-wide: `config_hash()` of the applied config, the startup `config_hash` at generation 0; the `cere` identity's `config_hash` stays the startup one |

### Sessions

Sessions store no content: each revision records a message count and a keyed digest of the message prefix.

- `POST /v1/cere/sessions` → `201 {"session_id":"sess_<32 hex>","revision":0}`.
- `GET /v1/cere/sessions/{id}` → `{"session_id","revision","message_count","model","parent"}`; `parent` is `null` or `{"session_id","revision"}`; `model` (M5 D7) is the session's bound model, `null` while unbound.
- `POST /v1/cere/sessions/{id}/fork` with exactly `{"revision": n}` → `201 {"session_id","revision":0,"parent_session_id","parent_revision"}`. The child inherits the parent's salt lineage, and its revision 0 is the parent's revision `n` (Q5). A revision that does not exist is `409 revision_conflict`.
- Continuation: send the full history in `messages` with `X-Cere-Session-Id` and `X-Cere-Expected-Revision`. The expected revision must be current and `messages[..message_count]` must match its digest, else `409 revision_conflict`. An assistant turn with tool calls matches only if each `arguments` string is echoed byte-exact (a client that re-serializes it gets `409 revision_conflict`); `content` `null` equals `""`, and `tool_calls[].index` and `type: "function"` are ignored (`validate.rs:52-80,773-823`). One writer per session at a time: a second concurrent writer gets `409 revision_conflict` before any backend call. A completed turn appends the assistant reply and advances the revision by one (returned as `cere.session_id`/`cere.revision`). A failed or cancelled turn releases the writer lease without advancing. More than `ledger.max_revisions_per_session` is `409 session_revision_limit`; a session without an active writer expires `ledger.session_ttl_ms` after its last commit.
- Model binding (M5 D7, `crates/cere-runtime/src/session.rs:300-313`): a session binds to the `model` of its first committed turn; a fork inherits its parent's binding. A turn on a bound session naming another model is `409 model_mismatch` (`param` `model`), checked after the idempotency lookup (a reused `Idempotency-Key` with another model stays `409 idempotency_conflict`) and before admission; nothing is journaled and the session is unchanged. A model the config no longer serves is `404 model_not_found` first (validation precedes the session check). The binding is journaled with the commit and survives restart and compaction; sessions journaled before M5 read back unbound and bind at their next commit.

### Operator routes: drain and undrain

`POST /v1/cere/workers/{worker_id}/drain` and `POST /v1/cere/workers/{worker_id}/undrain` (M3.5; no body) set or clear the operator drain intent of one configured worker, local or remote, in any state. They are authorized by the operator token from `[auth] operator_token_env` ([CONFIGURATION.md](CONFIGURATION.md)); the token is compared in constant time like a scope token. Checks run in this order:

| Case | Answer |
|---|---|
| no `[auth] operator_token_env` configured | `404` `not_found` (the routes do not exist) |
| `Authorization` absent, not `Bearer <token>`, or an unknown token | `401 unauthorized` with `WWW-Authenticate: Bearer` |
| a client scope token | `403` `forbidden` ("the operator routes need the operator token") |
| `worker_id` is neither a local worker nor a `[[federation.workers]]` id | `404` `worker_not_found` |
| the intent could not be journaled | `500` `internal_error`; the intent is unchanged |
| otherwise | `200 {"worker_id": "<id>", "draining": true}` (drain) or `false` (undrain) |

Errors use the envelope above with `type` `invalid_request_error` (`500`: `server_error`). Repeating a call is idempotent: it journals nothing and answers the same body. The intent is journaled (`worker_drain{worker, draining, at_ms}`), survives compaction and restarts, and is cleared only by undrain: neither Suspect, Lost, recovery nor a re-registration at a higher epoch clears it. A drained local worker gets no new requests, finishes its running ones and reads `draining` while it is otherwise ready. A remote worker's intent is stored even before its first Register and sent as `desired_state` `DRAINING` in every accepted heartbeat reply. The agent then fences its admission (reports `fenced` and refuses `SubmitWork`), so a draining remote worker's Joining rounds skip the smoke: it reads `draining` once registered, reconciled, leased and matching its pins, including after Lost and at a new agent epoch. Undrain starts a new Joining round; the agent reports `open` again and the worker reads `ready` only after that round's smoke passes.

### Operator routes: load and unload

`POST /v1/cere/workers/{worker_id}/load` and `POST /v1/cere/workers/{worker_id}/unload` (M3.6; no body, a body is ignored) record the operator's residency intent for one managed remote worker, in any state (Joining, Ready, Suspect or Lost). They share the drain routes' authorization and check order; after the worker id:

| Case | Answer |
|---|---|
| no `[auth] operator_token_env` configured | `404` `not_found` (the routes do not exist) |
| `Authorization` absent, not `Bearer <token>`, or an unknown token | `401 unauthorized` with `WWW-Authenticate: Bearer` |
| a client scope token | `403` `forbidden` |
| `worker_id` is neither a local worker nor a `[[federation.workers]]` id | `404` `worker_not_found` |
| a local worker, or a remote worker last described in attached mode | `409` `model_unmanaged` |
| a remote worker not described since this `cered` started | `409` `worker_not_described` |
| the intent could not be journaled | `500` `internal_error`; the intent is unchanged |
| otherwise | `202 {"worker_id": "<id>", "desired": "resident"\|"unloaded", "intent_seq": <n>, "model": {…}}` |

`model` is the worker's `/readyz` `model` object after the call. Every call is a new intent, also when it repeats the current one: it is journaled (`worker_residency{worker, desired, intent_seq, at_ms}`, `intent_seq` one above the worker's previous intent) before the answer, survives compaction and restarts, and the coordinator acts on the latest intent only. A managed worker is `ready` only while its described model state is `ready` under this `cered`'s deployment lock and `desired` is not `unloaded`; otherwise it stays `joining` with `model.state` set. `unload` takes the worker out of admission before it answers: no new request is granted to it once the `202` is sent (requests already running on it finish). `load` lets it pass the readiness round again. A running `cered` always has a pinned deployment, so there is no `deployment_unpinned` case.

`desired` `unloaded` takes a worker out of admission only while it was last described as managed (`model.managed` `true`); a worker last described in attached mode cannot get the intent (`409 model_unmanaged`). The coordinator issues `LoadModel` for `resident` while the agent reports `unloaded` or `draining`, and `UnloadModel` for `unloaded` while it reports `loading`, `ready`, `draining` or `failed`; a `failed` model is loaded again only after a new `load` call (no implicit retry). Known limit: while the worker is not `ready`, `model.state` is refreshed once per probe round, so it can lag the agent by up to 5 s.

A local native replica of a multi-replica deployment (`[[deployments.native.replicas]]`, m32n design note D10) is unloaded and loaded in process instead: `unload` needs the operator's drain intent (`409 worker_not_draining`) and no request admitted on the card (`409 requests_in_flight`), releases its executor and answers `202 {"worker_id", "native": "unloaded"}`; `load` makes the card's next probe run the load and SMOKE again (Ready at epoch + 1) and answers `202 {"worker_id", "native": "loading"}`, except after a sticky fault whose one reload failed (`409 worker_faulted`; a `cered` restart recovers it). Nothing is journaled for these. Every other local worker stays `409 model_unmanaged`.

`GET /v1/cere/cards` (operator token only, same auth and order; m32n design note D18, F15: it shows every scope's traffic) answers `200 {"cards": {<worker_id>: {...}}}` with one entry per native replica of a multi-replica deployment (`{}` otherwise): `device_uuid`, `state`, `epoch`, `loaded`, `rows_max`, `active_rows`, `kv_pool_tokens`, `reserved_pool_tokens`, `open_sessions`, `fifo_waiters`, `preemptions`, `prefix_hits`, `committed_tokens`, `decode_tokens_per_s` (committed since the previous read), `spec_verify_steps`, `spec_accepted_drafts`, `spec_accept_length` (null without a speculate round) and `free_mib` (null until the GPU phase), and `prefix_cache`: the card's prefix cache counters, the object of [`GET /v1/cere/prefix_cache`](#operator-route-prefix_cache) or null when it has none. Load counters are 0 while the card is not loaded and restart at each load.

### Operator route: prefix_cache

`GET /v1/cere/prefix_cache` (operator token only, same auth; the counters cover every scope's traffic) answers `200 {"workers": {<worker_id>: {"loaded": bool, "prefix_cache": object | null, "reason": null | string}}}` with one entry per local `native_cuda` worker, so it also serves the single form, where `GET /v1/cere/cards` is `{}`. `prefix_cache` is the cumulative `cere_model_prefix_stats` of the loaded model, all unsigned integers but the flag: `hits`, `captures`, `capture_skipped`, `capture_page_mismatch` (captures the M210S-39 rule refused because the tree holds other pages for equal tokens: the signature of a cache that stalls when a conversation diverges inside a cached edge), `inserts`, `state_evictions`, `leaf_evictions`, `host_spills`, `host_loads`, `host_drops`, `alt_edges` (alternative edges added, `prefix_alt_edges` only) and `alt_edges_enabled` (boolean). Counters start at 0 when the model loads, so they restart at each load (`unload` then `load` of a replica); within a load they never decrease, and a `flush_cache` keeps them. Read two samples and take the delta. `prefix_cache` is null with a `reason`: `not_loaded` (replica unloaded), `cache_off` (`prefix_state_slots` 0), `export_missing` (the library predates `cere_model_prefix_stats`; an old library keeps serving) or `read_failed`. It carries only counters, never a prompt, token or namespace.

Since prefix-token design note PT0a, `prefix_cache` also carries, from `cere_model_prefix_capture_stats`: `capture_skipped_by_site` (`{"prefill_slot", "decode_track", "end_pair"}`, the captures skipped because no state slot was free at a prefill capture, at a decode track capture (counted once per ticket) and at an end-state capture (no slot pair); they sum to `capture_skipped`), `hit_shortfall_tokens` (prompt tokens drafting lookups recomputed because no draft state sat at the deepest prefill-chunk multiple their page match passed) and `hit_shortfall_lookups` (drafting lookups that lost any). Each is `null` on a library from before that export (the other counters still read).

### Operator route: metrics

`GET /metrics` (ops-hardening design note OH-05; operator token only, the same check as every operator route: without `[auth] operator_token_env` the route does not exist (`404`), a missing or unknown token is `401 unauthorized`, a client scope's token `403 forbidden`) answers `200` with the Prometheus text exposition format 0.0.4 (`Content-Type: text/plain; version=0.0.4; charset=utf-8`). The families, their labels and meaning are listed in [OBSERVABILITY.md](OBSERVABILITY.md#prometheus-metrics); they are counters and gauges of every scope's traffic and never carry prompt or output text, a token, a scope id or a request id. A scrape reads each loaded native worker's prefix cache counters (one driver round trip per worker) and is otherwise in-memory.

### Operator route: flush_cache

`POST /v1/cere/workers/{worker_id}/flush_cache` (M2.10, m210 design note D11) drops every device and host entry of a local `native_cuda` worker's prefix cache, like SGLang's `/flush_cache?timeout=30`. The body is empty or exactly `{"timeout_s": t}` with `t` a number from 0 to 30 (default 30). The executor refuses a flush while a request is in flight or a session holds a cache hit; the route retries until `timeout_s` runs out.

| Case | Answer |
|---|---|
| no `[auth] operator_token_env` configured | `404` `not_found` (the routes do not exist) |
| `Authorization` absent, not `Bearer <token>`, or an unknown token | `401 unauthorized` with `WWW-Authenticate: Bearer` |
| a client scope token | `403` `forbidden` |
| the body is not a JSON object | `400 invalid_json` |
| any key other than `timeout_s` | `400 unsupported_parameter` |
| `timeout_s` not a number from 0 to 30 | `400 invalid_value` |
| no configured worker has this id | `404 worker_not_found` |
| the worker is not a local `native_cuda` worker | `409 worker_not_native` |
| the native worker is not loaded yet | `503 worker_not_ready` |
| the profile runs no prefix cache (`prefix_state_slots` absent or 0, e.g. shipped `native-g0.toml`) | `200` `{"worker_id": id, "prefix_cache": "off"}` |
| the executor stayed busy until `timeout_s` | `409 worker_busy` |
| flushed | `200` `{"worker_id": id, "prefix_cache": "flushed"}` |

### Operator routes: session owner and migration

A session has an owner: the worker its turns run on. `owner_generation` is `0` while it has none (before its first turn) and grows by one on every owner change: the first turn's pin, a turn re-pinned away from an owner that is not ready, and a migration. `GET /v1/cere/sessions/{id}/owner` reads it and `POST /v1/cere/sessions/{id}/migrate` moves it (M4). Both take a session of any scope and share the drain routes' authorization; checks run in this order (the body checks are the migrate route's):

| Case | Answer |
|---|---|
| `cered` is stopping | `503 shutting_down` |
| no `[auth] operator_token_env` configured | `404` `not_found` (the routes do not exist) |
| `Authorization` absent, not `Bearer <token>`, or an unknown token | `401 unauthorized` with `WWW-Authenticate: Bearer` |
| a client scope token | `403` `forbidden` |
| the body is not a JSON object | `400 invalid_json` |
| `to_worker` or `expected_owner_generation` is absent | `400 missing_required_parameter` (`param` names it) |
| any other key than those two and `force` | `400 unsupported_parameter` |
| `to_worker` is not a string, `expected_owner_generation` not a non-negative integer, `force` not a boolean | `400 invalid_value` |
| the session is unknown or expired | `404 session_not_found` |
| the session's owner generation is not `expected_owner_generation` | `409 owner_generation_conflict`; `error.worker` (the current owner, or `null`) and `error.owner_generation` name the current owner |
| `to_worker` is neither a local worker nor a `[[federation.workers]]` id | `404 worker_not_found` |
| `to_worker` belongs to another `[[deployments]]` entry than the session's bound model (an unbound session: than its owner's; an unbound session without owner skips this check) (M5 D8) | `409 model_mismatch` (`param` `model`) |
| `to_worker` is not ready (joining, draining, suspect or lost) | `409 worker_not_eligible` |
| `to_worker` already owns the session | `409 already_owner` |
| `force` is `true` and the owner is ready | `409 owner_healthy` |
| `force` is absent or `false` and a turn holds the session's writer lease | `409 session_busy` |
| the move could not be journaled | `500` `internal_error`; nothing changed |
| otherwise | `200 {"session_id", "worker": "<to_worker>", "owner_generation": <n + 1>, "revision", "mode": "replay"}` |

The owner read answers `200 {"session_id", "worker", "owner_generation", "revision"}` (`worker` is `null` while the session has no owner) or `404 session_not_found`.

A migration copies no state (`mode` `replay`): the client sends the full history with every turn anyway, and the new owner reconstructs the context from it, so the next turn there gets no prefix-cache hit. The revision does not change. The move is journaled (`session_owner{session_id, worker, owner_generation, revision, digest, at_ms}`) before it applies, survives compaction and restarts, and refreshes the session's TTL. A refusal changes nothing; repeating a successful request reads the move as `409 owner_generation_conflict` naming the new owner. A turn runs on the owner current when it takes the writer lease, so a migration that committed before that is honoured; without `force`, a migration never lands while a turn holds the lease.

`force: true` takes over from an owner that is not ready (or from no owner), also while a turn holds the lease: the lease is broken and that turn is cancelled with reason `session_owner_superseded` (aborted on its worker if it was running). If its output still completes there, its commit is refused and it ends `failed` `session_owner_superseded`; if the abort lands first it ends `cancelled` `session_owner_superseded`. Either way the revision does not advance, the client gets `409 session_owner_superseded` (the unary body, the stream's error event, the status API's `reason`), and the next turn at the same revision runs on the new owner. Every owner change is logged to stderr as `cered event=session_owner session=<id> worker=<worker> generation=<n> cause=pin|repin|migrate|force`.

### State teleport (NetTeleport S1)

net-teleport design note 4.2 L2, 4.3, D-T1..D-T7. Moves one cached prefix-cache state between two native installs (or two scopes of one install). Both routes need a `native_cuda` deployment with the prefix cache on, served by one card (a multi-replica deployment is refused), and the header `X-Cere-State-Key: <64 hex>`: the client's 32-byte key. It is never stored or logged, and the server keeps no copy of a blob. One export or import runs at a time per process.

**Export.** `POST /v1/cere/state/export` with a JSON body `{"model", "destination_tier": "own"|"team"|"provider", ...}` plus either `"tokens": [ids]` or the chat body (`messages`, `tools`, template kwargs; images are refused), which is validated and rendered exactly as `POST /v1/chat/completions` renders it. The source first refuses a `destination_tier` outside the scope's `[[auth.scopes]] allowed_tiers` (default `["own"]`). It then exports the deepest cached state of those ids in the caller scope's namespace and answers `200` with `Content-Type: application/vnd.cere.state-blob`, `Content-Length`, `X-Cere-State-Tokens` (the cached depth), `X-Cere-State-Image-Bytes` and `X-Cere-State-Compat-Id`, streaming the blob.

**Blob.** `CERESTB1`, a little-endian u32 header length, the JSON header `{format, library_sha256, profile_id, layout_id, state_compat_id, image_sha256, image_bytes, tokens, source_tier, allowed_tiers, created_unix_ms, frame_bytes, salt, key_check}`, then the `CERESNP1` image in 4 MiB frames. Each frame is AES-256-GCM ciphertext plus its 16-byte tag. The frame key is HKDF-SHA256(key, salt, `"cere state teleport v1 aead"`). Frame `i` uses nonce `0^4 || be64(i)` and AAD `prefix || header || le64(i) || last`, so an edited, reordered, truncated or extended blob fails to open. `key_check` (HKDF of the same key and salt, another info) tells a wrong key from a tampered blob. `state_compat_id` is SHA-256 over the library SHA-256, the layout id and the numerics-changing lever selections (D-T3). Teleport admits on it instead of `profile_id`; preemption keeps its strict check.

**Import.** `POST /v1/cere/state/import?model=<model>` with the blob as the body. Before any key use, the header is checked against this install: size cap, library, layout, compat id, and this install's `server.tier` against the blob's `allowed_tiers`. The frames are then decrypted one by one into one `mlock`ed buffer (never pageable; zeroed on drop), the image digest is checked, and the state is inserted under the caller scope's own namespace (D-T2). `200 {"imported_tokens", "image_bytes", "state_compat_id", "tier"}`. The next chat of that scope with the same prefix hits the cache. An image exported from a drafting profile is flagged NO_SPECULATION: its first turns after import decode without drafts (R-T6).

A busy executor (the library refuses prefix-cache export and import while a ticket is in flight) is retried until `state.busy_wait_ms` (default 30 s), then refused. Every refusal imports nothing; the client then replays the conversation (D-T1). Refusals:

| Condition | Status, `code` |
|---|---|
| `X-Cere-State-Key` absent or not 64 hex digits | `400 state_key_invalid` |
| Not a format-1 blob (magic, header, frame size, length) | `400 state_malformed` |
| Blob from another library build | `409 state_library_mismatch` |
| Another state layout | `409 state_layout_mismatch` |
| Same library and layout, other numerics-changing levers | `409 state_compat_mismatch` |
| Destination tier not allowed (export: the scope's `allowed_tiers`; import: this install's tier not in the blob's) | `403 state_tier_not_allowed` |
| Image larger than `state.max_blob_bytes` (default 4 GiB; export and import) | `413 state_oversize` |
| The key does not open the blob | `400 state_wrong_key` |
| Authentication failed (edited, reordered, truncated or extended) | `400 state_tampered` |
| The image buffer could not be `mlock`ed | `503 state_memlock` |
| The executor stayed busy past `state.busy_wait_ms` | `409 state_busy` |
| No free state slot, pages or arena room | `409 state_capacity` |
| Nothing cached for the prefix (export) | `404 state_no_prefix` |
| Not a single-card native deployment with a prefix cache, images, or a library without the export | `409 state_unsupported` |

Each call logs one stderr line `cered state <export|import> scope=<scope> outcome=<ok|code> tokens=<n> image_bytes=<n> ms=<n>`: never the key, token ids or content (4.1). An image is decrypted whole into one locked buffer; a chunked library import is S2 work.

### LoRA adapters (vLLM routes)

A native deployment with `[deployments.native.lora]` (the opt-in `-v50` profile, `configs/runtime/native-g0-spec-lora.toml`) serves PEFT LoRA adapters on its base model through the vLLM runtime-adapter routes. Without the table the routes do not exist (`404`). The table is refused with `[[deployments.native.replicas]]` and with `[[federation.workers]]` (an adapter lives in one executor's pool). The executor library must export `cere_model_lora_reserve`, `cere_model_lora_load`, `cere_model_lora_unload` and `cere_session_set_lora` (ABI v4, optional symbols); a library without them fails the load with a `lora` problem naming them.

| Key | Meaning |
|---|---|
| `max_adapters` | resident adapters, 1..=64 (the pool `cere_model_lora_reserve` sizes at load; `CAPACITY` past the memory budget fails the load) |
| `max_rank` | largest adapter rank, 1..=256 |
| `adapter_root` | absolute directory; every adapter path must resolve inside it (symlinks resolved) |
| `preload` | `[{name, path}]` (absolute paths, at most `max_adapters`, unique names) loaded before the backend reports ready; a failed one fails the load |

All five keys need a restart (`reload.rs`).

`POST /v1/load_lora_adapter {"lora_name": "<name>", "lora_path": "<dir>"}` reads the PEFT directory (`adapter_config.json` and `adapter_model.safetensors`; `lora_path` relative to `adapter_root` or absolute inside it), checks it against the base model and loads it into a free slot. `POST /v1/unload_lora_adapter {"lora_name": "<name>"}` frees its slot. Both need a client bearer token (as `/v1/models`, so an operator token is not required), take `api.max_request_body_bytes` bodies and answer vLLM's plain-text `200`:

| Case | Answer |
|---|---|
| missing/unknown bearer token | `401 unauthorized` |
| `cered` is shutting down | `503` (the shutdown error of every route) |
| body not JSON, unknown shape or over the limit | `400 invalid_json` |
| load without `lora_path` | `400 invalid_value` (`param` `lora_path`) |
| bad name (`^[A-Za-z0-9][A-Za-z0-9_.:-]{0,127}$`), a served model's name, an already loaded name, no free slot, a path outside `adapter_root` or missing, a malformed adapter, or the executor refusing it (`ARGUMENT`/`UNSUPPORTED`/`CAPACITY`) | `400 invalid_lora_adapter` |
| unload of a name not loaded | `404 lora_adapter_not_found` |
| unload while a request holds the adapter or a session is bound to its slot (executor `BUSY`) | `409 lora_adapter_busy` (retriable once the requests end) |
| the native model is not loaded | `503 not_ready` |
| any other executor failure | `500 lora_adapter_failed` |
| load done | `200` `Success: LoRA adapter '<name>' added successfully.` |
| unload done | `200` `Success: LoRA adapter '<name>' removed successfully.` |

The adapter checks: `peft_type` `LORA`, `r` 1..=`max_rank`, finite `lora_alpha` (scale `lora_alpha/r`, `lora_alpha/sqrt(r)` with `use_rslora`), no bias, no DoRA, BF16/F16/F32 `lora_A`/`lora_B` tensors (sent as BF16) for `q_proj`, `k_proj`, `v_proj`, `o_proj` (full-attention layers only) and the shared expert's `gate_proj`, `up_proj`, `down_proj`, with A `[r, in]` and B `[out, r]` matching the base config. The adapter's identity is the SHA-256 of its config and weights bytes.

A loaded adapter is a model: `GET /v1/models` lists one card per adapter after the base cards (`{"id": "<name>", "object": "model", "created": <load unix time>, "owned_by": "cere", "parent": "<base served model>", "root": "<resolved dir>", "max_model_len": <base>}`), `GET /v1/models/<name>` answers it, and a chat request (also `/v1/messages`, `/v1/responses`) with `"model": "<name>"` runs on the base deployment with the adapter: its policy, limits and scope rules are the base model's, the response's `model` is the adapter name. The request holds the adapter until it ends, so an unload meanwhile is `409`. Requests naming the base model are unchanged (bit-identical with or without adapters loaded).

Isolation: an adapter request's prefix-cache namespace is the base namespace mixed with the adapter's SHA-256 (`lora::namespace`), so no cached prefix crosses between the base and an adapter or between two adapters; base requests keep theirs. The idempotency digest of an adapter request adds `lora_adapter_sha256`, so the same body against a reloaded different adapter is a new request. An adapter session is never snapshotted (`cere_session_snapshot` is `UNSUPPORTED` for it): it is kept resident instead of parked by host spill/preemption.

### Research (WeightLab)

Opt-in and off by default; overview in [RESEARCH_HOOKS.md](RESEARCH_HOOKS.md). The `/v1/cere/research/*` routes exist only on a native deployment with `[deployments.native.research]` (the dev profile `-v57`, `configs/runtime/native-g0-spec-research.toml`; docs/CONFIGURATION.md); without the table they are not registered (`404`) and every request runs today's code path. Every route needs the operator bearer (`[auth] operator_token_env`, as the other operator routes): `404` when no operator key is configured, `403` with a client scope token, `401` with none or an unknown one. The executor library must export `cere_model_research_reserve`, `cere_model_research_plan_load`, `cere_model_research_plan_unload`, `cere_session_set_research`, `cere_model_research_capture_read` and `cere_model_research_capture_free` (ABI v4, optional symbols 42-47); a library without them fails the load. Errors use the operator routes' JSON error envelope.

**Plans.** `POST /v1/cere/research/plans` registers a plan:

```json
{"capture": [{"point": "native.layers.L.attn_mix.out", "layers": [0, 5], "positions": {"prompt": [[0, 128], [200, 210]], "generated": true}}],
 "interventions": [{"kind": "add", "point": "native.layers.L.attn_mix.out", "layers": "all", "positions": {"generated": 64},
                    "vector_id": "<id>", "alpha": -2.0}],
 "seed": 7, "target": "coding_output_volume"}
```

* `point`: a capture point with `L` as the layer: `native.layers.L.{attn_mix,mlp_mix}.in` (the 4-stream residual state, 10,240 BF16 columns, 20,480 B per row), `native.layers.L.{attn_mix,mlp_mix}.out` (2,560), `native.layers.L.gemm.attn_qkv.out` (13,312; full-attention layers 3, 7, ..., 47), `native.layers.L.gemm.gdn_qkv.out` (10,240) and `native.layers.L.gemm.gdn_z.out` (6,144) (GDN layers), `model.layers.L.self_attn.o_proj` (full-attention) / `model.layers.L.linear_attn.out_proj` (GDN) (2,560), `native.layers.L.gemm.moe_router.out` (the 512 router logits), `native.layers.L.moe_route` (the chosen expert ids I32[10] and gate weights F32[10], 80 B), `model.layers.L.mlp.experts`, `model.layers.L.mlp.shared_expert.down_proj` (2,560), `native.layers.L.gemm.moe_shared_down.in` (the shared expert's down_proj input, 640 BF16 columns, 1,280 B per row; capture only), `native.final_mix.out` (2,560), `native.logits.topk` (`top_k` 1..=64 ids I32 and log-softmax F32, 8·top_k B) and `native.logits` (the 248,320 BF16 logits, 496,640 B; generated positions only, at most 8).
* `layers`: a list of layer indices in [0, 48) at which the point exists, or `"all"`; the final points (`native.final_mix.out`, `native.logits*`) take none (layer 48).
* `positions`: `prompt` ranges `[first, end)` of absolute positions (sorted, disjoint, non-empty, at most 64) and/or `generated` (`true`: every generated token; `N` >= 1: the first N). Under speculation only accepted positions are kept; MTP drafts are never captured or edited.
* `interventions` (kinds `add`, `ablate_zero`, `ablate_mean`, `replace`, `expert_bias`, `expert_mask`, `expert_force`; `vector_id`, `alpha`, `cols` `[b, e)`, `experts`, `weights` where the kind needs them): edits applied in place at the point; the vectors they name come from the vector routes below.
* `target` must be in the allowlist (today: `coding_output_volume` only). `seed` (u64) makes an unseeded sampled request of a bound scope seeded: the first 8 bytes (LE) of sha256(seed LE ‖ CERE session id ‖ revision LE), so arms repeat.

| Case | Answer |
|---|---|
| unknown point or kind, a layer where the point does not exist, bad positions, cols mismatch, unknown vector, `target` not in the allowlist, the executor refusing the plan (`ARGUMENT`) | `400 invalid_research_plan` |
| the plan's capture bound (sum over capture ops and layers of rows x row bytes, `generated: true` counted at the deployment's context) over `max_capture_bytes_per_request` | `400 research_budget_exceeded` (the error carries `bound` and `cap`) |
| `max_plans` plans registered | `507 research_plans_full` |
| registered | `200 {"plan_id", "plan_sha256", "capture_bound_bytes"}` (`plan_sha256`: sha256 of the parsed plan's canonical JSON) |

**Bindings.** `POST /v1/cere/research/bindings {"scope", "plan_id"}` makes every request of client scope `scope` (a `[[auth.scopes]]` `scope_id`) run under the plan (`404` unknown plan or scope, `409` scope already bound). `DELETE /v1/cere/research/bindings/{scope}` unbinds (`404` not bound). `DELETE /v1/cere/research/plans/{plan_id}` deletes a plan (`404` unknown; `409 research_plan_busy` while it is bound or a request runs under it).

**Requests under a plan.** Admission reserves the request's capture bound (the same formula with its prompt length and `max_tokens`) in the host ring (`host_buffer_bytes`, all captures not yet drained); when it does not fit the request is `503 research_buffer_full` and nothing runs. Every reply that ran under a plan (`/v1/chat/completions`, `/v1/completions`, `/v1/messages`, `/v1/responses`) carries `X-Cere-Research-Plan: <plan_sha256>`. Planned rows run eager (no decode graph); a plan's sessions are never snapshotted or preempted. An intervening plan mixes its `plan_sha256` into the prefix-cache namespace, so no cached state crosses between plans or with the base; a capture-only plan keeps the base namespace. A plan that captures prompt positions skips the prefix-cache lookup for its requests (a hit has no prefill to capture). With no plan bound, requests are unchanged (bit-identical).

**Captures.** `GET /v1/cere/research/captures?scope=&after=` lists the finished, undrained captures (`after`: a request id; only captures finished after it): `{"captures": [{"request_id", "scope", "plan_id", "plan_sha256", "prefix_lookup": "skipped"|"used", "bytes", "created", "tensors": [{"name", "point", "layer", "positions", "dtype": "BF16"|"I32"|"F32", "shape": [rows, cols], "sha256"}]}]}`. `GET /v1/cere/research/captures/{request_id}` streams the capture once as a safetensors file (tensor names `<point>/L<layer>`, two-part points `<point>.<part>/L<layer>`, e.g. `native.layers.L.moe_route.ids/L3`, final points layer 48; one row per captured position, ascending; `__metadata__` `request_id`, `plan_sha256`) and then frees it; `404` unknown or already drained.

**Vectors.** `POST /v1/cere/research/vectors?name=<name>`: the body is a safetensors file with exactly one BF16 tensor of shape `[cols]` or `[rows, cols]` (rows 1..=4,096, the `replace` kind's source rows; `[cols]` is one row), every value finite and at most `CERE_RESEARCH_MAX_PLAN_BYTES` (4 MiB) of data; `name` is 1..=128 bytes of `[A-Za-z0-9._-]`. It answers 200 `{"vector_id": "vec_<n>", "sha256", "rows", "cols"}`, `sha256` the hex SHA-256 of the whole body (the record's `vector_sha256`); ids count uploads from 1 within one `cered` process and vectors do not survive a restart. `DELETE /v1/cere/research/vectors/{id}` answers 200 `{"vector_id", "deleted": true}`. Refusals change nothing: `400 invalid_research_vector` (body, name, dtype, shape, size or a non-finite value), `409 research_vector_exists` (name taken), `507 research_vectors_full` (`max_vectors` stored), `404 research_vector_not_found`, `409 research_vector_busy` (a loaded plan names it). A plan's `vector_id` must name a stored vector whose `cols` equal the edited column range (else `400 invalid_research_plan`).

### `POST /v1/messages` (Anthropic Messages)

M2.14 D3 (m214 design note). **Off by default.** `/v1/messages` and `/v1/messages/count_tokens` exist only when some `[[deployments]]` entry sets `api_compat_anthropic = true`; no shipped config sets it (exposure is needs-human N6). With the flag off on every entry the routes are not registered and answer exactly as any unknown route does today (`404`, empty body). A request whose `model` selects an entry without the flag gets `404` in the Anthropic envelope. Authentication is the bearer token only: the Anthropic `x-api-key` header is not accepted (N6), so a request carrying only it is `401`.

The surface is a host-side translation into the chat pipeline ([`anthropic.rs`](../crates/cere-runtime/src/anthropic.rs)): the request is validated as SGLang's `protocol.py` validates it and converted as SGLang's `_convert_to_chat_completion_request` converts it; the chat body then goes through the chat validator, admission, journal, deadlines and cancel unchanged, on both backends. The subset:

* `system` (a string or text blocks), `messages` with string content or `text` blocks (joined as the pinned chat template renders them), `tool_use` (an assistant tool call; `input` becomes `arguments` as Python `json.dumps` writes it) and `tool_result` (a tool message). Inline `role: system` messages before the first user/assistant message are merged into the leading system message after the top-level `system` (`\n`-joined), as SGLang does; since ApiFit (AF-L2) an inline system message after a turn (as a coding agent sends its reminders) stays at its position and renders by the chat rule above (an empty one is dropped).
* `tools` (`name`, `description`, `input_schema`, kept as the client's bytes) and `tool_choice` `auto` (the default with tools) and `none`. Since ApiFit (AF-L6) `tool_choice` `any` is sent as chat `required` and `tool` as `{"type": "function", "function": {"name"}}` (SGLang's conversion) on a deployment whose profile has `tool_calls_constrained` decode combinations; the chat rules then apply (the constrained combination for the sampler mode). Elsewhere they stay `400`, as before.
* `max_tokens` (required), `stop_sequences`, `temperature`, `top_p`, `stream`, `metadata`.
* Dropped fields (ApiLenient D4, Q6): `metadata`, a truthy `betas`, `output_config.task_budget`, `thinking.budget_tokens` where it is not enforced, and any other top-level key are accepted and dropped as SGLang drops them, and reported in `X-Cere-Ignored-Params` and `cere_request_params_total{surface="anthropic"}` (no longer as stderr lines); a key that is not a plain field name is reported as `unlisted`. `deterministic` (a reserved CERE extension) is `400`.
* `thinking` absent or `disabled` is the deployment default. On a deployment whose profile declares M2.12's `thinking_toggle`, `thinking` `enabled` / `adaptive` is sent as `chat_template_kwargs.enable_thinking: true` and `output_config.effort` `low` / `medium` as `reasoning_effort`, as SGLang converts them; other efforts are `400 invalid_value` (m212 D13). Without `thinking_toggle` both are `400 unsupported_parameter`. `thinking.budget_tokens` is validated as SGLang validates it (required with `enabled`, at least 1024, not allowed with `disabled`). On a `native_cuda` deployment it is enforced (ApiFit AF-L7): it is sent as the chat extension `thinking_budget` (above), so the `thinking` block holds at most `budget_tokens` tokens and the `text` block follows; on `sglang_http` it is accepted and not enforced, as SGLang does. `adaptive` thinking and effort carry no budget.
* `top_k`, forwarded as sent when the profile lists it in `sampling_params` (ApiFit AF-L6), else `400` (M2.7 sampling capability); image blocks are `400` (M2.13).
* `document` blocks (DocInput, doc-input design note), in user content and inside a `tool_result`'s content: `{type: "document", source, title?, context?, citations?}` with `source` `{type: "base64", media_type: "application/pdf" | "text/plain", data}`, `{type: "text", media_type: "text/plain", data}` or `{type: "content", content: [text blocks]}`. Each renders to text as a chat `file` part does (`<document title=".." media_type=".." pages="N">`, `<context>` when given, `<page number="i">` per PDF page, `</document>`; a PDF with no text on any page gives the chat part's `[no text found in this PDF's N pages: …]` line), joined with the neighbouring text; a `tool_result` holding one (a coding agent's `Read` of a PDF: `[{text: "PDF file read: …"}, {document}]`) becomes one tool message. The chat limits apply (32 MiB per document, 100 PDF pages and 1 MiB of rendered text per request, history included). `citations: {enabled: true}`, `url` and `file` sources, an image inside a `content` source, another media type and an encrypted PDF are `400 unsupported_parameter`; a broken document, a limit or a reader defect is `400 invalid_value`; the message names the block (`messages[i].content[j].source`, …) and never quotes the data. Another unknown block type keeps SGLang's message.

**Sampling.** The chat rules of the deployment apply to the converted body, exactly as on `/v1/chat/completions`: on a `native_cuda` deployment an absent `temperature` samples with the model's defaults (1.0 / `top_k` 20 / `top_p` 0.95, m27 design note D10), and a deployment whose profile validates greedy only needs `temperature: 0`.

**Responses.** Unary: SGLang's `message` object (`msg_` id, `content` blocks `thinking` / `text` / `tool_use`, `stop_reason`, `usage` with `input_tokens`/`output_tokens`). `stop_reason` is `end_turn` for a natural stop and for a matched stop string (as SGLang reports it; `stop_sequence` is never produced), `max_tokens` on a `length` finish and `tool_use` for tool calls. Stream: SGLang's events as `event: <type>` + `data: <json>` frames (`message_start`, `content_block_start`, `content_block_delta`, `content_block_stop`, `message_delta`, `message_stop`); no `id:` lines, no `cere` object, no `accepted` event and no `[DONE]`. Usage follows Anthropic's semantics (ApiFit AF-L8): on a local `native_cuda` deployment `message_start` carries `usage.input_tokens` = the encoded prompt's token count (the `count_tokens` answer) and `output_tokens: 0`; the final `message_delta` carries the cumulative `output_tokens` and, when the PREFILL hit the prefix cache, `input_tokens` = prompt − hits and `cache_read_input_tokens` = hits (hits are known only after the PREFILL, so `message_start` cannot split them). On `sglang_http` and remote-worker deployments the count is unknown when the stream opens: `message_start` carries `input_tokens: 0` and the final `message_delta` carries `input_tokens` (and `cache_read_input_tokens` when SGLang reports cached tokens). Unary `usage` is `input_tokens` = prompt − hits, `output_tokens`, and `cache_read_input_tokens` only when hits > 0 (SGLang's shape). `cache_creation_input_tokens` is never sent: cered's prefix cache has no billed write. A failure after the stream opened closes the open block and ends with an `error` event and `message_stop`. The `X-Cere-Request-Id` header is set on every accepted request.

**`count_tokens`** takes the same body without `max_tokens` and answers `{"input_tokens": n}`. On a `native_cuda` deployment the tokenizer sidecar renders and encodes the converted conversation exactly as the chat path does for `usage.prompt_tokens` (no context check, nothing submitted); on an `sglang_http` deployment SGLang's own `/v1/messages/count_tokens` answers for the client's bytes. The conversion and the chat validation run first; a count is never admitted or journaled, and needs a Ready local worker (else `503`).

**Errors** use SGLang's Anthropic envelope: `{"type":"error","error":{"type","message"}}`, where `type` follows the HTTP status (`invalid_request_error` 400, `authentication_error` 401, `permission_error` 403, `not_found_error` 404, `request_timeout_error` 408, `rate_limit_error` 429, `overloaded_error` 503, else `api_error`) and a 5xx message is `Internal server error`.

**Context errors (ApiFit AF-L3).** A prompt that does not fit is refused with Anthropic's own two wordings, the ones a coding agent recognizes (api-fit design note F12): prompt alone over the context → `400` `{"type":"error","error":{"type":"invalid_request_error","message":"prompt is too long: N tokens > M maximum"}}`; prompt within the context but prompt + `max_tokens` over it → message ``input length and `max_tokens` exceed context limit: N + K > M, decrease input length or `max_tokens` and try again``. Both the native `context_length_exceeded` and SGLang's `context_overflow` (counts read from SGLang's text) map this way, unary and as the stream's `error` event; `/v1/chat/completions` and `/v1/responses` keep their own codes and messages.

**Idempotency and resume.** As for `/v1/responses` below: the surface is part of the request digest, so an `Idempotency-Key` reused across chat and `/v1/messages` is `409`; a unary replay returns the retained Anthropic body byte for byte; a streamed request is never replayed, and `GET /v1/cere/requests/{id}/events` on it answers `409 stream_not_replayable` (`X-Cere-On-Disconnect: continue` does not apply). The journal records the request as chat's, plus `"surface": "anthropic"`.

### `POST /v1/responses` (OpenAI Responses, stateless)

M2.14 D4 (m214 design note). **Off by default.** The three `/v1/responses` routes exist only when some `[[deployments]]` entry sets `api_compat_responses = true`; no shipped config sets it (exposure is needs-human N6). With the flag off on every entry the routes are not registered and answer exactly as any unknown route does today (`404`, empty body). A request whose `model` selects an entry without the flag gets `404 not_found`.

The surface is a host-side translation into the chat pipeline ([`responses.rs`](../crates/cere-runtime/src/responses.rs)): the converted chat body goes through the chat validator, admission, journal, deadlines and cancel unchanged, on both backends. It mirrors SGLang's non-harmony `OpenAIServingResponses` for this subset:

* `input`: a string (one user message) or items: messages (`role` `user`/`assistant`/`system`/`developer`, content a string or `input_text`/`output_text` parts, joined), `function_call` (an assistant tool call) and `function_call_output` (a tool message). `developer` becomes `system`, as SGLang normalizes it; a system/developer item after the first message renders in place by the chat rule (ApiFit AF-L1).
* `instructions`: a leading system message (a leading system item is appended to it).
* `tools`: function tools only (`{type:"function", name, description?, parameters?, strict?}`), converted to chat tools; built-in tools (`web_search_preview`, ...) are `400 unsupported_parameter`.
* `tool_choice`: `auto` (the default with tools) and `none`. `required` with no function tool is `400 invalid_value` (as SGLang refuses it); `required` with tools and named functions are `400 unsupported_parameter`: chat supports them since M2.8, but mapping them here is the Responses adapter's follow-up (m28 design note D13).
* `max_output_tokens`, `temperature`, `top_p`, `stream`.
* `reasoning.effort` `low` / `medium` / `xhigh`: sent as `reasoning_effort` with `chat_template_kwargs.enable_thinking: true` on a deployment whose profile declares M2.12's `thinking_toggle`, else `400 unsupported_parameter`; other efforts are `400 invalid_value` (m212 D13). `reasoning.summary`: `400 unsupported_parameter`. Image parts: `400 unsupported_parameter` (M2.13).
* Every other field is `400 unsupported_parameter`, never dropped.

**Sampling.** On an `sglang_http` deployment the chat body carries SGLang's effective Responses sampling (`ResponsesRequest.to_sampling_params`): `max_completion_tokens = max_output_tokens - 2` (SGLang's headroom; a `max_output_tokens` below 3 is `400 invalid_value`), and an absent `temperature` / `top_p` is sent as `0.7` / `1.0`, so cered's backend body equals what SGLang's own route would generate. On a `native_cuda` deployment an absent `temperature` / `top_p` is not filled in and the chat rules of that deployment apply to the converted body, exactly as on `/v1/chat/completions` and `/v1/messages`: native samples it with the model's `generation_config.json` defaults (1.0 / `top_k` 20 / `top_p` 0.95, m27 design note D10), and a deployment whose profile validates greedy only needs `temperature: 0`.

**Stateless.** cered keeps no response store (sessions remain `/v1/cere/sessions`). `previous_response_id` and `background: true` are `400 unsupported_parameter`. `store` (SGLang's default is `true`) is treated as `false` when absent and echoed `"store": false`; `store: true` is `400 unsupported_parameter`. ApiLenient D4: `user`, `safety_identifier`, `metadata`, `prompt_cache_key`, `prompt_cache_retention` and `service_tier` follow the chat inert rules; they and `store: false` are dropped and reported in `X-Cere-Ignored-Params` and `cere_request_params_total{surface="responses"}`; `deterministic` is `400`. `GET /v1/responses/{id}` and `POST /v1/responses/{id}/cancel` are authenticated (bearer) and then always `404 not_found` with a "stateless" message, whatever the serving state or the deployments' flags.

**Responses.** Unary: SGLang's `response` object (`resp_` id, `output` items `reasoning` / `message` / `function_call`, `status` `completed` or `incomplete` with `incomplete_details.reason: max_output_tokens` on a `length` finish, `usage` with `input_tokens`/`output_tokens`). Stream: SGLang's `responses_stream_generator_non_harmony` events as `event: <type>` + `data: <json>` frames (`response.created`, `response.in_progress`, `response.output_item.added`, `response.content_part.added`, `response.output_text.delta`, ..., `response.completed`), with `sequence_number` from 0; no `id:` lines, no `cere` object, no `accepted` event and no `[DONE]`. A failure after the stream opened ends with `response.failed`. The `X-Cere-Request-Id` header is set on every accepted request.

**Errors** use SGLang's envelope, not the chat one: `{"error":{"message","type","param":null,"code":<HTTP status>}}`, where `type` is the CERE error code (`unsupported_parameter`, `invalid_value`, `not_found`, `unauthorized`, `idempotency_conflict`, ...). Messages never echo a Python traceback or file path.

**Idempotency and resume.** The surface is part of the request digest, so an `Idempotency-Key` used on chat and then on `/v1/responses` (or the reverse) is `409 idempotency_conflict`. A unary replay returns the retained Responses body byte for byte. A streamed request is never replayed (`409 stream_not_replayable`), and `GET /v1/cere/requests/{id}/events` on it answers `409 stream_not_replayable`: Responses streams are not continue-mode streams (`X-Cere-On-Disconnect: continue` does not apply).

### Not implemented

`required`/named `tool_choice` on `/v1/responses` and, on a profile without `tool_calls_constrained` decodes, `any`/`tool` on `/v1/messages` (m28 design note D13, ApiFit AF-L6), post-validation of constrained output, `n > 1`, prompt logprobs and `echo`, content parts outside user and tool messages, remote image URLs, images on federated deployments or on a native profile without an image decode combination, PDF page images, document citations, uploaded files (`file_id`) and remote documents (`url` sources), durable (restart-surviving) stream buffers, model load/unload of a local backend (only a managed remote worker's model is loaded and unloaded, through its agent, and a native replica's card in process, [above](#operator-routes-load-and-unload)), a capabilities endpoint, and more than one `native_cuda` executor per process outside the replicas of one native deployment. All of these are rejected or absent rather than approximated. Two `native_cuda` executors in one process are supported for the two-card deployment (`[[deployments.native.replicas]]`, one executor per card, `configs/runtime/native-2gpu.toml`, m32n design note; [MULTI_GPU.md](MULTI_GPU.md)). Tool calls are returned, never executed.

## Required operations (design contract)

| Operation | Contract |
|---|---|
| health | process alive; does not imply model ready |
| readiness | exact model/profile loaded; smoke gate passed; capacity known |
| submit | auth scope, request ID, payload digest, deadline, model, token budget |
| cancel | idempotent cancellation intent; terminal acknowledgement is separate |
| status | request state, actual path, queue/compute timing; scoped authorization |
| session create/fork | explicit parent revision; server-issued handle; scope checked |
| continuation | expected revision + exact append; reject conflicting writers |
| metrics/capabilities | operator endpoint; no raw prompts/KV/token hashes by default |

## Structured output and tools

Tool-call IDs, JSON schema, grammar constraints, logprobs, nonzero-temperature sampling and speculation must be supported **together** by the selected profile or rejected before execution. Grammar/sampler state participates in rollback/checkpoints. A tool parser cannot turn an unverified draft into a committed tool call. Exact replay of rendered tool history is separate from JSON equivalence.

## Event sequence

accepted -> zero or more token/tool-delta events -> exactly one terminal event. Events have monotonic sequence numbers and committed token offsets. SSE keepalive is not a generated token and must not count as TTFT. Track first generated token and first user-visible token separately when reasoning is streamed separately.

## Retry/idempotency

Canonical payload hashing includes semantically relevant options and exact input identity. A duplicate ID with conflicting content returns conflict. Session revisions serialize writers; forks produce new session IDs. A disconnected client may query status; retrying a partially streamed request without a resume contract never implicitly regenerates it.

## Security

Loopback default, bounded body/context/output sizes, credential references outside config, constant scope authorization for session/state endpoints. Backend URLs and model filesystem paths come only from operator config. No client-selected backend egress, arbitrary host paths or remote-code trust.

## Model lifecycle operations (v0.4 contract)

Operator/admin control eventually needs operations to list approved recipes and instances, request load/preload, acquire/release bounded residency leases, drain, and unload. Ordinary inference callers may select an approved recipe but cannot submit arbitrary URLs, paths, images or placement commands.

The model-manager state reported to callers must distinguish `loading`, `ready`, `draining`, `unloading` and `failed`. A request routed to a loading model may wait within its deadline; it must not start a duplicate model load.

## Context overflow

Default behavior is explicit rejection. Any truncation/compaction must be requested through an authorized semantic operation and recorded in request diagnostics.

## Stream resumption

An opt-in resume contract uses request ID + event cursor with bounded replay. It resumes the same live request and does not imply worker-crash recovery or exactly-once tool execution. The M1 implementation is [Stream resume](#stream-resume) above; see [STREAM_RESUME.md](STREAM_RESUME.md).


## Worker RPC

The public/client inference API and the internal worker RPC (`ai.cere.worker.v2`, mTLS gRPC between `cered` and
`cere-worker`) are separate. The implemented subset, its auth profile, limits and reason codes are in
[WORKER_PROTOCOL.md](WORKER_PROTOCOL.md). SSH is not part of this API.
